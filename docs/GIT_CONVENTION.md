# Git Convention

## Branch

### `main`

- 배포 가능한 안정 버전을 유지한다.
- 직접 push하지 않는다.
- 운영 배포 또는 최종 제출 기준 브랜치로 사용한다.

### `dev`

- 개발 통합 브랜치로 사용한다.
- `feature` 및 `fix` 브랜치의 병합 대상이다.
- 작업 시작 전 항상 최신 상태로 pull한다.

### 작업 브랜치

새 기능은 `feature/{domainName}-{detail}`, 버그 수정과 기능 보완은
`fix/{domainName}-{detail}` 형식을 사용한다.

예시:

```text
feature/user-login
feature/project-dashboard
fix/auth-token-error
fix/api-response-format
```

작업 순서:

1. `dev` 브랜치를 최신화한다.
2. 작업 브랜치를 생성한다.
3. 기능 단위로 작업한다.
4. 커밋 후 원격 작업 브랜치에 push한다.
5. PR을 생성하고 코드 리뷰를 받는다.
6. 승인 후 `dev` 브랜치로 병합한다.

## Code Style

- Prettier와 ESLint를 사용한다.
- 세미콜론과 싱글 쿼트를 사용한다.
- 들여쓰기는 공백 4칸을 사용한다.
- 불필요한 `console.log`, 사용하지 않는 변수와 import를 제거한다.
- 변수와 함수는 camelCase, 컴포넌트와 클래스는 PascalCase를 사용한다.
- 상수는 UPPER_SNAKE_CASE를 사용한다.
- 파일명은 kebab-case 또는 역할 기반 이름을 사용한다.
- 코드만으로 의도가 명확하지 않을 때만 주석을 작성한다.
- 임시 주석은 작업 완료 전에 제거한다.
- TODO에는 담당자와 작업 목적을 함께 작성한다.

## Commit

```text
type: 작업 내용
```

| 타입 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 코드 변경 없는 문서 수정 |
| `style` | 논리 변경 없는 코드 스타일 수정 |
| `refactor` | 기능 변화 없는 리팩토링 |
| `test` | 테스트 코드 추가 및 수정 |
| `chore` | 빌드와 패키지 설정 등 기타 작업 |
| `design` | CSS 등 UI 디자인 변경 |
| `comment` | 필요한 주석 추가 및 변경 |
| `rename` | 파일 또는 폴더 이름 변경과 이동 |
| `remove` | 파일 삭제만 수행 |
| `!HOTFIX` | 치명적인 버그의 긴급 수정 |

커밋 하나에는 하나의 목적만 담고, 메시지만으로 변경 내용을 이해할 수 있게 작성한다.

## Pull Request

- 기능 단위 작업 완료 후 `dev` 브랜치를 대상으로 생성한다.
- 생성 전에 로컬 실행, 빌드, 테스트를 확인한다.
- 제목은 `[타입] #이슈번호 제목` 형식을 사용한다.
- 최소 1명 이상의 리뷰와 승인을 받아야 한다.
- 리뷰 의견 반영 후 재요청 코멘트를 작성한다.
- 충돌은 작업자가 해결하고 다시 확인을 요청한다.
- 빌드와 테스트가 통과하고 충돌과 체크리스트 미완료 항목이 없어야 병합한다.

PR 본문:

```markdown
## 관련 이슈
- close #이슈번호

## ✨ 작업 내용
-

## 스크린샷 / 테스트 결과
-

## 리뷰 포인트
-

## ✅ 체크리스트
- [ ] 커밋 메시지 컨벤션을 준수했는가?
- [ ] 로컬에서 빌드 및 테스트가 성공했는가?
- [ ] 불필요한 주석이나 console.log를 제거했는가?
- [ ] 관련 문서를 함께 수정했는가?
```
